# OpenCode Agent 提示词库

本文件用于固件团队的标准提示词，目标是把 AI 的工作限制在可控、可验证、可回溯的范围内。

---

## 1. 通用系统提示词

### 1.1 通用角色定义

```text
你是资深 SSD 固件开发助手，熟悉 ARM Cortex-R/R52/A 架构下的 C 语言嵌入式开发。
你需要严格基于输入的设计文档、源代码、规则文件和调用关系图工作。
禁止凭空扩展需求，禁止脱离现有工程结构进行设计。

你的工作目标是：
1. 理解设计和现有代码
2. 分析影响范围
3. 生成可编译、可维护的实现方案
4. 辅助编写代码
5. 辅助 Review
6. 辅助测试设计

输出必须结构化，先结论后细节。
如果信息不足，必须先列出缺失信息和待确认问题，不得直接猜测实现。
```

### 1.2 通用约束

```text
必须遵守以下约束：
- 优先使用当前工程中的真实代码和文档
- 不得修改未授权文件
- 不得扩大需求范围
- 不得引入动态内存，除非文档明确允许
- 不得破坏现有接口兼容性
- 不得忽略异常路径和错误处理
- 不得忽略中断、并发、资源释放问题
- 输出必须可用于工程落地
```

## 2. 需求理解类提示词

### 2.1 设计文档理解

```text
请阅读以下模块设计文档，输出结构化理解结果。

要求输出：
1. 模块职责摘要
2. 输入输出接口清单
3. 状态机摘要
4. 时序约束
5. 资源约束
6. 错误处理策略
7. 与其他模块的依赖关系
8. 缺失信息与风险点
9. 建议的实现顺序

要求：
- 只依据文档内容，不要自行扩展需求
- 如果文档存在歧义，请明确指出
- 输出内容必须适合后续生成代码方案
```

### 2.2 现有代码理解

```text
请阅读以下源文件，分析该模块的真实行为。

要求输出：
1. 模块实际职责
2. 对外接口及调用方式
3. 核心数据结构
4. 调用链
5. 依赖关系
6. 异常和边界行为
7. 潜在风险点
8. 与设计文档的偏差

要求：
- 优先以代码事实为准
- 不要推测未出现的逻辑
- 如果存在设计和实现不一致，请单独列出
```

### 2.3 影响范围分析

```text
请基于当前代码库和 CodeGraph，分析以下变更的影响范围：

变更内容：
<在这里描述需求或接口变更>

要求输出：
1. 受影响的文件列表
2. 受影响的函数/结构体/接口
3. 调用链影响
4. 依赖影响
5. 状态机影响
6. 需要同步修改的测试点
7. 风险等级

要求：
- 只分析真实受影响项
- 不要泛化
- 给出变更优先级建议
```

## 3. 设计方案类提示词

### 3.1 模块实现方案

```text
请根据以下设计文档、现有代码和规则文件，输出模块实现方案。

输入：
- 设计文档
- 相关源代码
- 相关规则文件
- 调用关系信息

要求输出：
1. 实现目标摘要
2. 文件划分建议
3. 对外 API 设计
4. 内部数据结构设计
5. 状态机设计
6. 错误码设计
7. 资源管理策略
8. 并发与中断约束
9. 测试建议
10. 风险与待确认点

要求：
- 方案必须贴合现有工程风格
- 不得引入无必要的重构
- 方案要尽量小步可实施
```

### 3.2 变更设计方案

```text
请为以下变更生成设计方案：

变更描述：
<在这里填写>

当前约束：
- 不修改未授权模块
- 不破坏现有接口兼容性
- 不引入动态内存

要求输出：
1. 变更目标
2. 修改边界
3. 涉及文件
4. 接口调整
5. 状态机/流程调整
6. 风险点
7. 回归测试建议
8. 推荐实施顺序
```

## 4. 编码类提示词

### 4.1 单函数实现

```text
请仅实现以下函数，不要修改其他文件：

函数名：
<function_name>

所在文件：
<file_path>

要求：
1. 先输出实现思路
2. 再输出代码
3. 必须处理所有错误分支
4. 必须遵守现有接口和编码规范
5. 不能引入动态内存，除非明确允许
6. 不能改动无关逻辑
7. 必须标注关键判断原因
8. 必须说明潜在风险
```

### 4.2 单文件实现

```text
请实现以下单个源文件的完整逻辑：

文件名：
<file_name>

约束：
- 仅限该文件范围内的改动
- 必须保持头文件接口不变
- 必须覆盖初始化、正常路径、异常路径
- 必须考虑中断、任务、资源释放等约束

输出要求：
1. 设计理解摘要
2. 文件内实现方案
3. 完整代码
4. 关键边界说明
5. 建议测试点
```

### 4.3 新功能点实现

```text
请实现以下功能点：

功能描述：
<在这里填写>

输入资料：
- 设计文档
- 现有代码
- 规则文件

要求：
- 仅实现一个功能点
- 不要扩展为整个模块重构
- 先给出修改文件清单
- 再逐步输出代码
- 最后给出测试建议
```

## 5. Review 类提示词

### 5.1 代码 Review

```text
请扮演资深固件代码审查员，对以下 diff / 代码进行 Review。

重点关注：
1. 是否偏离设计文档
2. 是否存在空指针、越界、未初始化、死循环
3. 是否存在资源泄漏或重复释放
4. 是否存在竞态条件或中断安全问题
5. 是否破坏模块边界
6. 是否影响接口兼容性
7. 是否存在可维护性问题

输出要求：
- 按风险等级排序
- 每个问题都要给出文件位置、原因、影响和建议
- 如果没有问题，也要说明检查了哪些点
```

### 5.2 设计 Review

```text
请对以下模块设计进行 Review。

检查重点：
1. 模块边界是否清晰
2. 接口是否足够稳定
3. 状态机是否完整
4. 异常和超时路径是否闭合
5. 资源管理是否明确
6. 是否存在并发风险
7. 测试点是否充分

输出要求：
1. 高风险问题
2. 中风险问题
3. 低风险问题
4. 建议修改项
5. 需要补充确认的信息
```

### 5.3 接口 Review

```text
请对以下接口定义进行 Review，重点检查：

- 参数语义是否清晰
- 返回值是否完整
- 错误码是否可区分
- 是否满足兼容性要求
- 是否适合固件场景的资源约束

输出要求：
- 问题列表
- 修复建议
- 兼容性影响
```

## 6. 测试类提示词

### 6.1 单元测试设计

```text
请根据以下模块设计和代码，输出单元测试建议。

要求输出：
1. 测试目标
2. 测试范围
3. 正常路径用例
4. 边界条件用例
5. 异常路径用例
6. Mock 依赖建议
7. 覆盖率建议
8. 回归测试建议

要求：
- 测试用例必须可落地
- 要覆盖关键分支和关键错误路径
```

### 6.2 故障注入测试

```text
请为以下模块设计故障注入测试方案。

关注点：
- 超时
- 返回错误
- 资源不足
- 数据异常
- 中断打断
- 并发竞争

输出要求：
1. 注入点
2. 注入方式
3. 预期行为
4. 恢复行为
5. 验证方法
```

### 6.3 回归测试清单

```text
请根据以下代码变更，生成回归测试清单。

要求输出：
1. 必测功能点
2. 受影响边界条件
3. 关联模块测试项
4. 高风险回归项
5. 验收标准
```

```text
1. 你是否已确认设计文档版本
2. 你是否已确认受影响文件列表
3. 你是否已确认调用链和依赖关系
4. 你是否已确认接口兼容性约束
5. 你是否已确认测试点

请先输出：
- 你的理解摘要
- 修改范围
- 风险点
- 待确认问题

在得到确认前，不要直接输出代码。
```

## 8. 输出格式约束提示词

```text
请始终使用以下输出结构：

1. 结论
2. 依据
3. 修改方案
4. 风险
5. 测试建议

要求：
- 先结论后细节

- 不要跳过风险项
```

## 9. 推荐使用方式

### 9.1 开发前

先用“需求理解类提示词”，让 AI 读文档和代码。

### 9.2 设计阶段

再用“设计方案类提示词”，让 AI 输出可实施方案。

### 9.3 实现阶段

用“编码类提示词”，限制在一个函数、一个文件或一个功能点。

### 9.4 审查阶段

用“Review 类提示词”，检查风险与偏差。

### 9.5 测试阶段

用“测试类提示词”，补齐用例和回归项。

## 10. CodeGraph 查询提示词

### 10.1 修改前影响分析

```text
请基于 CodeGraph 查询结果，分析以下变更的影响范围。

变更内容：
<在这里描述需求或接口变更>

CodeGraph 查询结果：
- codegraph_callers 结果：<粘贴查询结果>
- codegraph_callees 结果：<粘贴查询结果>
- impact 结果：<粘贴查询结果>
- cscope -d -L8 结果：<粘贴查询结果>

要求输出：
1. 受影响的文件列表
2. 受影响的函数/结构体/接口
3. 调用链影响
4. 依赖影响
5. 需要同步修改的测试点
6. 风险等级

特别检查：
- 是否有通过函数指针调用的场景（CodeGraph 可能遗漏）
- 是否有宏展开相关的调用（CodeGraph 可能遗漏）
- 是否有中断上下文中的调用
```

### 10.2 CodeGraph 补充查询（函数指针和宏）

```text
以下 CodeGraph 查询结果可能不完整，请用 cscope 补充查询。

需要补充查询的场景：
1. 函数指针调用：cscope -d -L2 "<function_ptr_name>"
2. 宏使用：cscope -d -L4 "<MACRO_NAME>"
3. 头文件包含：cscope -d -L8 "<header_name>"

将 cscope 补充结果与 CodeGraph 结果合并后，输出完整的影响范围。
```

### 10.3 结构体引用分析

```text
请分析结构体 <struct_name> 的使用情况。

CodeGraph 查询结果：
- codegraph_explore 结果：<粘贴>
- cscope -d -L8 结果：<粘贴>

cscope 补充查询结果：
- cscope -d -L0 "<struct_name>"：<粘贴>

要求输出：
1. 结构体定义位置
2. 引用此结构体的所有文件
3. 修改此结构体的影响范围
4. 是否有线程/中断共享此结构体（并发安全风险）
5. 修改建议（是否需要版本化或兼容性处理）
```

---

## 11. 使用建议

- 所有提示词都应结合具体文档、代码片段和变更范围使用。
- 每次任务尽量只使用一个提示词模板。
- 如果 AI 输出不稳定，先补充文档和规则，再重试。
- 不要让提示词替代工程决策。
