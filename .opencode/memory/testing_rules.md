# Testing Rules

SSD 固件测试规则。AI 生成测试建议时必须遵守，测试设计时必须覆盖。

## 1. 单元测试要求

### 1.1 必测模块

以下模块必须有单元测试：

| 模块 | 必测原因 | 最低覆盖要求 |
|------|----------|-------------|
| FTL 映射表 | 数据安全核心 | 分支覆盖 ≥ 90% |
| NAND 驱动读写 | 数据安全核心 | 分支覆盖 ≥ 90% |
| NVMe 命令解析 | 功能正确性 | 分支覆盖 ≥ 85% |
| Buffer 管理 | 资源泄漏风险 | 分支覆盖 ≥ 85% |
| ECC 纠错 | 数据安全核心 | 分支覆盖 ≥ 90% |
| 坏块管理 | 数据安全核心 | 分支覆盖 ≥ 85% |

### 1.2 测试分类

- **正常路径测试**：验证功能在正确输入下的行为
- **边界条件测试**：验证功能在极端输入下的行为
- **异常路径测试**：验证功能在错误输入下的行为
- **并发测试**：验证多核/多任务/中断场景下的行为

### 1.3 边界条件必须覆盖

- 数组：索引 0、最大索引、最大索引+1
- 计数器：0、1、最大值-1、最大值、最大值+1
- 地址：对齐地址、非对齐地址、首地址、末地址
- 超时：刚好超时、刚好不超时
- 长度：0、1、最大值、超出限制

## 2. 测试框架与 Mock 规范

### 2.1 Mock 层设计

以下外设接口必须可 Mock：

| 接口 | Mock 原因 |
|------|----------|
| NAND 寄存器读写 | 硬件依赖 |
| DMA 传输 | 硬件依赖 |
| 中断控制器 | 时序依赖 |
| 时钟/定时器 | 时序依赖 |
| DRAM 访问 | 环境依赖 |
| NVMe SQ/CQ | 主机接口依赖 |

### 2.2 Mock 规则

- Mock 接口与真实接口签名必须一致
- Mock 必须能模拟正常返回和各种错误返回
- Mock 必须能记录调用次数和参数
- Mock 必须能注入延迟，模拟时序
- 测试结束后必须恢复真实接口

### 2.3 测试隔离

- 每个测试用例必须独立运行，不依赖其他用例的副作用
- 全局状态在测试前初始化、测试后清理
- 测试顺序不影响结果
- 测试之间不共享可变状态

## 3. 固件专项测试

### 3.1 断电恢复测试

| 场景 | 测试点 |
|------|--------|
| 写入中断电 | 数据完整性、映射表恢复 |
| 擦除中断电 | Block 状态正确性、坏块检测 |
| GC 过程中断电 | 数据不丢失、映射表完整 |
| 映射表保存中断电 | 双备份恢复、CRC 校验 |

### 3.2 NAND 异常测试

| 场景 | 测试点 |
|------|--------|
| ECC 可纠正错误 | 重试成功、弱块标记 |
| ECC 不可纠正错误 | 坏块标记、数据重映射 |
| 编程失败 | 重试、块标记、数据保护 |
| 擦除失败 | 坏块标记、替换块分配 |
| 写干扰 | 相邻 Page 数据校验 |

### 3.3 并发与中断测试

| 场景 | 测试点 |
|------|--------|
| 多核同时访问映射表 | 锁保护、数据一致性 |
| ISR 打断 FTL GC | 状态机正确恢复 |
| DMA 传输中中断 | Buffer 一致性 |
| 双队列并发处理 | 命令顺序正确 |

### 3.4 性能测试

| 指标 | 最低要求 | 测试条件 |
|------|----------|----------|
| 4K 随机读延迟 | ≤ 规格值 | 单队列深度 |
| 4K 随机写延迟 | ≤ 规格值 | 单队列深度 |
| 顺序读带宽 | ≥ 规格值的 90% | 多队列深度 |
| 顺序写带宽 | ≥ 规格值的 90% | 多队列深度 |
| GC 影响写延迟 | ≤ 规格值 × 3 | GC 进行中 |

## 4. 覆盖要求

### 4.1 新增功能

- 新增功能必须定义覆盖点
- 修改接口必须补充回归用例
- 修复 Bug 必须补充回归用例（防止复发）

### 4.2 覆盖率标准

| 模块类型 | 行覆盖 | 分支覆盖 |
|----------|--------|----------|
| 数据安全核心 | ≥ 90% | ≥ 85% |
| 功能核心 | ≥ 80% | ≥ 75% |
| 辅助功能 | ≥ 70% | ≥ 60% |
| 调试/日志 | ≥ 50% | ≥ 40% |

### 4.3 不可覆盖路径

- 硬件故障恢复路径（需故障注入）
- 断电路径（需特殊设备）
- 多核竞争路径（需压力测试）

对于不可覆盖路径，必须在测试报告中标注：
- 为什么不可覆盖
- 通过什么替代方式验证（代码审查/故障注入/纸上推演）

### 4.4 Bug Injection Evidence（**强制**，per `superpowers-test-driven-development` Iron Rule）

> 背景：test-after 流程的固有风险是"测试会适配实现，而非适配需求"。一个"通过一次"的测试从未失败过——无法证明它能抓 bug。Bug injection 循环（red-green-verified）强制测试在某次被破坏时失败，从而**证明**测试的 falsifiability。

#### 强制要求

每个**新引入的公共 API**（对外暴露的函数、结构体字段、QOM property）必须满足：

1. **正常路径注入（≥1）**：测试断言"在正常输入下行为正确"——然后注入一个会破坏该断言的 bug，**测试必须失败**；revert bug 后测试必须再次通过。
2. **错误路径注入（≥1）**：测试断言"在异常输入下行为正确（错误码 / NULL / 边界）"——然后注入一个会绕过错误处理的 bug，**测试必须失败**；revert 后通过。
3. **边界条件注入（≥1，可选）**：针对边界值（0、max、空）的测试同样需要 red-green 验证。

#### Bug Injection 循环操作步骤

```
1. 运行测试，确认 PASS（baseline）
2. 在代码中刻意引入最小 bug（一行 sed 级别）：
   - 正常路径：改返回值 / 改条件判断 / 注释掉关键行
   - 错误路径：移除错误检查 / 注释掉错误返回
3. 重新运行测试，确认 FAIL
4. 观察失败信息：是否准确指出错误位置和原因？
5. 撤销注入（git checkout / sed revert）
6. 重新运行测试，确认 PASS
```

#### 证据归档

每次 bug injection 循环的 4 步（baseline → injected fail → revert → baseline pass）必须记录到 `verify-report.md` 的 "Bug injection 证据" 段。不可覆盖路径（如硬件依赖）必须显式标注 N/A 并说明理由。

#### 自动化脚本

提供 `bash .opencode/scripts/inject_bug.sh <source_file> <sed_pattern> <test_binary>` 辅助：
- 备份原文件
- 应用 sed 注入
- 跑测试，捕获 exit code
- 恢复原文件
- 输出 "PASS/FAIL/REVERTED" 三态结果

> **缺失后果**：未做注入验证的测试，在 Review 中标记为"测试有效性未确认"，可能阻塞 `/opsx:archive`。

### 4.5 覆盖率与 bug injection 准入

| 准入项 | 阈值 | 阻塞 archive? |
|--------|------|---------------|
| 公共 API bug injection 覆盖率 | **100%**（不可覆盖需 N/A + 理由）| 是 |
| Spec Requirement → 实现追溯 | **100%** | 是 |
| Spec Scenario → 测试追溯 | **100%** | 是 |
| 行覆盖（数据安全核心）| ≥ 90% | 是 |
| 分支覆盖（数据安全核心）| ≥ 85% | 是 |

## 5. 测试命名与文档

### 5.1 测试用例命名

```
test_<模块>_<函数>_<场景>_<期望结果>

示例：
test_nand_read_page_ecc_correctable_return_ok
test_ftl_map_lba_invalid_range_return_error
test_nvme_process_cmd_admin_identify_return_data
```

### 5.2 测试文档

每个测试用例必须包含：
- 测试目的
- 前置条件
- 测试步骤
- 期望结果
- 实际结果（执行后填写）

## 6. AI 辅助测试建议

AI 生成测试建议时，必须按以下格式输出：

```markdown
### 测试建议：<模块名>

#### 正常路径
| 用例 ID | 场景描述 | 输入 | 期望输出 | 优先级 |
|---------|----------|------|----------|--------|

#### 边界条件
| 用例 ID | 场景描述 | 边界值 | 期望输出 | 优先级 |
|---------|----------|--------|----------|--------|

#### 异常路径
| 用例 ID | 场景描述 | 异常注入 | 期望行为 | 优先级 |
|---------|----------|----------|----------|--------|

#### Mock 依赖
| 依赖接口 | Mock 行为 | 验证点 |
|----------|----------|--------|
```

人工确认后纳入正式测试文档。

### 测试场景清单（强制）

即使项目无自动化测试框架，AI 也必须对每次代码修改输出「测试场景清单」：

| 修改点 | 验证方法 | 预期结果 |
|--------|---------|---------|
| <具体修改位置> | 编译检查 / 运行时日志 / 边界输入 | <期望行为> |

不可跳过此步骤。无测试框架不能作为省略理由——编译验证和运行时日志是最低要求的验证手段。

## 测试时序规则（test-after）

### 6.1 时序要求

- 生产代码实现后，**同一变更内**必须补充对应测试。
- 禁止跨变更补测试（"下次再补" = 永远不会补）。
- 测试和实现代码在同一 tasks.md 的同一个 task 中完成，不可拆分到不同 task。

### 6.2 test-after 的可信度要求

test-after 的固有风险是"测试会适配实现，而非适配需求"。为缓解此风险：

- 测试场景必须在编码前定义（在 design.md 或 task 描述中列出测试场景清单）。
- 测试必须基于 design.md 中的场景写，而非基于代码读到的实现细节。
- Review 时必须检查：测试是否覆盖了 design.md 中声明的所有场景。

### 6.3 硬件依赖代码的测试策略

对于直接操作硬件寄存器、DMA 描述符、ISR 的代码，单元测试可能不可行：

- 尽量通过 HAL 接口抽象将业务逻辑与硬件操作解耦，使业务逻辑可测。
- 硬件实现层（寄存器操作等）用集成测试或仿真验证。
- 不可覆盖路径必须在 review.md 中标注：为什么不可覆盖、通过什么替代方式验证。

详细规则见 `.opencode/skills/superpowers-test-driven-development/SKILL.md`。
