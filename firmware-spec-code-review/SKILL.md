# 固件规范与实现一致性审查

交付可复核的要求—实现关系和差异报告。区分文档表达、代码事实、审查判断与运行证据，不以实现现状改写冻结要求。方法提炼及许可见[来源说明](references/sources.md)。

## 进入与适用范围

取得指定规范/AC 的准确版本及批准状态、代码 commit/工作树快照、目标配置、审查范围和已有行为分析。草案也可比较，但结果保持研究性质，不能将草案差异直接判为违反正式要求。

从当前任务与阶段判断比较目的并写入报告，不机械询问：

- **基线差距分析**：Open/Design 比较现有实现与本次目标，区分既有承诺和计划新增行为。新 AC 尚未实现应进入实施范围/设计输入，不能仅凭差距判为交付缺陷；已有承诺的违反仍如实记录。
- **交付一致性审查**：Build 交付后或 Verify 核对本次声称完成的范围；必需行为缺失或违反作为候选实现问题处理，按原合同判断证据和回流。

阶段只是判断线索；若同一任务兼有两种目的，按要求标明比较对象与预期实现时点，避免混用。Greenfield 尚无实现时只记录基线能力待建立，不伪造代码检查结果。

没有表达应有行为的来源时，使用 [firmware-context-analysis](../firmware-context-analysis/SKILL.md) 建立实现上下文并报告规范缺口；不能从代码推导要求再自证一致。仅缺少部分资料时仍可审查有充分来源的范围，显式列出不可读和未审部分。

遇到术语、历史设计或依赖事实缺口，使用 [comet-domain-context](../comet-domain-context/SKILL.md)，遵守当前阶段的来源绑定规则。上游报告只是线索，重要结论仍回读规范原文与实现。

## 要求到实现的追踪

继承当前 Story/AC、适用约束及来源 ID，再回规范原文核对本次范围的完整性，不另建平行产品要求清单。为分析拆出的条件、分支、阈值和失败结果保留父 AC/约束及原文定位；继承清单有遗漏时显式提出来源义务缺口，不能静默忽略。新发现的来源义务或语义问题交责任阶段修订，派生解释另标候选；不得自行扩大冻结范围。冲突或模糊要求保留待决，不能选择最容易满足的解释。

对每项要求定位实现入口、约束建立点、调用者/被调用者、共享状态及相关失败分支。检查保证是否覆盖要求适用的路径，结合构建宏、函数指针、外部依赖和运行环境说明分析边界。读到一个同名函数或通过一个 UT 不等于追踪完成。

保证可能位于调用者、初始化、调度/模块合同或硬件边界；定位依据并检查当前条件下是否成立，未核实的外部保证保持待验。共享实现发现逐项绑定受影响 Story/AC，影响未知的对象标待复核，不默认整个 Wave 失败。

按需核对反方向：实现是否增加未记载的输入限制、错误结果、完成边界或跨模块依赖。更严格不自动等于更安全；可能改变兼容性或拒绝合法输入，按实际后果判断。

逐项采用[判定与报告约定](references/report.md)中的静态分析判定；这些标签不是 Comet 状态或测试通过结果。声称未找到实现时附搜索范围、符号/别名、调用路径及结果。无法覆盖必要路径时保留无法判断或部分检查，不把检索无结果当作绝对不存在。

## 独立反驳重要发现

先分开记录事实与解释：真实运行失败及原始日志立即保留并交当前 Owner 处理，不能等待独立 Reviewer 才承认失败，也不能因尚未复核而允许通过；其根因、路径可达性和是否违反某条规范可以仍是候选解释。测试失败是否属于有效行为 RED 等判断继续遵守当前阶段合同。

对会影响返工/放行的高风险、争议或推断性解释，组织独立反驳。优先复用现有独立责任主体：未主导 Build 且未形成该候选解释的 Verify Owner 可以承担，无需固定再加一层 Reviewer；若解释由 Verify Owner 本人提出且需要独立反驳，则由另一获授权分析者或工程师承担。普通一致性记录按风险抽查，不逐项强制派工。

提供原始要求、准确源码、候选解释、实际证据和未审范围，请独立主体寻找能推翻解释的依据，而非赞同原结论。环境/权限不支持时保留未复核解释并交责任人，实际失败及未满足证明义务不会因此消失。

独立检查至少关注两侧：

- **实现侧**：是否由调用者、初始化、替代路径或其他机制满足要求；反例路径是否真实可达；构建配置是否匹配？
- **规范侧**：是否遗漏条件/例外，混淆草案或目标版本，把推荐方案当强制机制，或误解术语/完成边界？

Owner 汇总反驳证据，修正或撤回被推翻的解释并保留理由和原始事实；有分歧时保持待决。记录独立主体、输入版本、检查范围、结论和证据。执行失败或资源不足时明确哪些解释“未独立复核”，不把整个报告里的真实事实一并降为猜测；自我复查不能冒充独立反驳。

## 完成与交接

每项范围内要求都有判定与依据，或明确未检查原因；需反驳的解释有记录或未复核状态；规范外行为、不可读材料和分析限制显式可见。重要结论交付受影响 AC/决定、可推翻解释的场景、所需观察/证据和下一责任人，供 Design 明确 Oracle 或 Verify 补验，不在本 Skill 中修改批准测试语义。按报告约定保存在授权位置，源码、规范和冻结 AC 只读。严重性按实际数据、资源、可用性及兼容性后果与项目规则描述，不照搬上游安全审计评级，不编造故障复现。

交给当前 Stage Owner：规范语义问题回 PRD-Split/工程师；方案问题回 Design；实现问题回 Build；证据不足交 Verify 补验。技术资料与代码冲突由有权责任人决定哪个需要改，不能为一致而自动修改文档或代码。

报告只能作为 Design Review/Verify 的分析输入。即使所有静态判定一致，仍须满足原始 AC 的证明要求、独立 Verify、有效工程师接受和 Comet Gate。来源/代码/配置变化后重评受影响项和独立结论，原报告保留历史版本。
